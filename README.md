# flight-hx

Haxe externs generated by the Rust tooling in
[Flight](https://github.com/flighthq/flight), targeting native FFI and web ESM.
The transpiled Haxe implementation backend, separate TypeScript compiler
dependency, and flight-cpp adapters have been removed.

The checked-in copy comes from Flight `develop` revision
`49c510e875461a9235b24ee846015ec1b47acd2a`: 3,401 generated files plus provenance,
including 2,782 function externs per target, selected from 5,718 native ABI exports.
Output is copied unchanged; this repository owns intake, packaging, and checks.

## Consume

The Haxelib name is `flight`. Add `-lib flight` and use the generated `flight.*`
API. The package macro loads only `generated/externs`; upstream dispatch selects
HL, cpp, or `js` with `-D flight_esm`. Other targets and the removed `flight_hx`
backend fail at compile time.

```haxe
import flight.Math;
import flight.Geometry;

final value = lerp(0, 10, 0.25);
final vector = createVector2(3, 4);
final length = getVector2Length(vector);
```

For static ESM output, also use `--macro EsmGenerator.use()` and `-dce full`.
A bundler can then consume the generated imports. The runtime module requirements
below must be satisfied before executing a consumer.

## Runtime integration boundary

All generated declarations type-check on HL, cpp, and JS. An extracted consumer
archive also type-checks on all three targets and emits static ESM imports. A
separate C++ probe links the real Rust `flight-ffi` library and checks scalar
calls, opaque allocation, field access/mutation, and release.

**End-to-end Haxe runtime support is not yet established by the upstream output:**

- cpp externs name `flight_*` C symbols, but Flight does not yet emit a general
  C declaration header or hxcpp link configuration. Consumers need that bridge
  and the matching `flight-ffi` binary; no old flight-cpp implementation is used.
- HL declarations expect a native library named `flight`. A HashLink native shim
  is not supplied by these copied externs. Layout offsets were generated on
  Linux x64; other ABI layouts have not been validated.
- JS externs import module `flight` with `flight_*` exports, including field
  accessors. They do not directly consume the existing `@flighthq/*` TS ESM
  exports. A matching ESM runtime is required; none is fabricated here.
- Generated native handles do not establish automatic ownership or disposal.
  The binary probe explicitly calls its matching `flight_free_*` export.

These gaps are distinct from a successful type-check. The package and CI do not
claim full Haxe native/web execution or parity with the removed implementations.

## Develop

```sh
npm ci
npm run setup                   # pinned Haxe 4.3.7 + hxcpp metadata
npm run rehydrate               # pinned Rust Flight workspace
npm run generate -- --allow-network # first build may need Cargo downloads
npm run check                   # offline regeneration + local validation
npm run package:haxelib         # dist/flight-0.6.0.zip
```

Use the pinned Rust 1.96.0 toolchain in `rust-toolchain.toml`. The driver also recognizes a repository-local toolchain in
`.artifacts/rust/{cargo,rustup}`. It does not install Rust automatically.
`FLIGHT_ROOT` or `--flight-root <path>` selects another clean Flight checkout;
update the lock when intentionally changing the source revision.

```sh
npm run generate:externs:check   # reject changed, missing, or extra copied files
npm run gate:surface             # verify provenance/hashes and all three targets
npm run gate:package             # deterministic ZIP + extracted consumer + ESM emission
npm run gate:native-ffi          # Linux/macOS C++ probe against built flight-ffi
npm run test:externs-driver      # orchestration/failure-isolation fixtures
npm run check:externs:upstream   # run Flight's own check script
```

Flight's own `scripts/check-haxe-bindings.sh` passes all three targets with the
pinned toolchain. Cargo 1.100 changes the build directory layout and breaks the
script's old glob; the intake driver uses Cargo-reported output paths. Toolchain
identity and host architecture are recorded alongside the offsets in provenance.

See [extern intake](tools/externs/README.md) for the exact generation recipe.
