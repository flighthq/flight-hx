# flight-hx

Haxe externs generated by the Rust and TypeScript tooling in
[Flight](https://github.com/flighthq/flight), targeting native FFI and web ESM.
The transpiled Haxe implementation, separate TypeScript compiler dependency,
and flight-cpp adapters have been removed.

The source is Flight `develop` revision
`c52653a12e10251ab93970f71a6bc0c4dcbe21fa` plus the [producer patches](patches/flight/README.md).
Generated Haxe is copied unchanged from Flight. Provenance records the revision
and patch hashes.

## Consume

The haxelib name is `flight`. Install a release ZIP containing binaries for your
platform, then add `-lib flight` or use this in a Lime project:

```xml
<haxelib name="flight" />
```

`include.xml` selects native binaries, configures linking, and deploys shared
libraries. The package macro also supports ordinary hxcpp and HashLink builds
without Lime. Consumers do not need Rust, Cargo, or Node.

Windows native binaries are x64. For ordinary hxcpp builds, pass `-D HXCPP_M64`
explicitly; hxcpp can otherwise target x86 even on a 64-bit host:

```sh
haxe -lib flight -cp examples/ffi-smoke -main Smoke -D HXCPP_M64 -cpp out
```

For Lime, select x64 with `haxelib run lime test windows -64`.

```haxe
import flight.Math;
import flight.Geometry;

final value = lerp(0, 10, 0.25);
final vector = createVector2(3, 4);
final length = getVector2Length(vector);
freeVector2(vector);
```

Native handles require the matching release function; allocation does not imply
automatic disposal. Unsupported targets and the removed `flight_hx` backend fail
at compile time.

Native node constructors and hierarchy queries return `FlightNode` handles.
Release each returned handle with `node.free()`, or use
`FlightNode.freeNullable(node)` when it may be null. The scene retains its own
references to attached nodes. The C header documents the release function for
other owned results.

Use `name`, `node2dAlpha`, and `node2dVisible` on native node handles. Read the
native blend mode through `node2dBlendMode` and write it with
`setNode2dBlendMode(value, present)`. Raw field writes do not invalidate
appearance. Call `flight.Node.invalidateNodeAppearance(node)` when needed.
ESM node types expose `name`, `alpha`, `visible`, and `blendMode` through the SDK's
object fields. The ESM appearance setters advance the node's appearance revision.

Native compression functions return `ByteResult`, with `length`, `get(index)`,
`toBytes()`, and `free()`. `toBytes()` creates a managed Haxe copy.
To build a native bitmap region, pass the handle returned by `shareBitmap`,
which takes ownership of the original bitmap. The region retains a reference
after the caller releases the shared handle with `freeBitmapRef`.

Use `freeOwnedByteReader` for owned byte readers in `flight.Buffer`,
`freeUnitSignal` for command-history signals, and `freeCommandHistoryRef` for
the history handle. Scalar and optional scalar tuple returns are also supported.
Native public string properties use UTF-8 C strings.

Flight verifies native Haxe extern signatures against the generated C header
and HashLink shim. The upstream policy still lists retained callbacks and
selected native carriers that require dedicated Haxe support. Native host-provider
FFI for Flight's Rust desktop and headless hosts is TODO.

## Native layout

```text
native/include/flight_ffi.h          generated C ABI declarations
native/bin/<platform>/              shared Flight runtime (.so/.dylib/.dll)
native/lib/<platform>/              iOS static archive or Windows import library
native/artifacts/<platform>.json    source identity and artifact checksums
ndll/<platform>/flight.hdll         HashLink adapter
ndll/Windows64/flight.lib           HashLink adapter import library for Lime
```

Ordinary shared libraries live in `native/bin`; `ndll` is used only for the
HashLink adapter selected by Lime's native module machinery. The binaries and
artifact manifests are ignored by Git. Release ZIPs include the staged platforms
after checking their provenance and checksums. An unstaged platform fails with
a missing-binary error instead of falling back to another implementation.

Platform folders are `Linux64`, `LinuxArm64`, `Mac64`, `MacArm64`, `Windows64`,
`iPhoneOSArm64`, `iPhoneSimulator64`, and `iPhoneSimulatorArm64`. Desktop hxcpp
links the shared library; iOS links `libflight_ffi.a`. For a cross build, set
`flight_native_platform` before the Flight haxelib entry, for example:

```xml
<set name="flight_native_platform" value="iPhoneSimulatorArm64" />
<haxelib name="flight" />
```

The native runtime checks run a consumer installed from the ZIP through hxcpp,
HashLink, Lime Linux, and Lime HashLink. HashLink also loads the entire generated
native declaration surface. The smoke calls cover scalar math, allocation,
field access/mutation, and release. This does not establish every API's runtime
behavior. Locally these have passed on Linux x64. CI now runs the same installed
consumer on Intel macOS and Windows, and builds/links iOS device and simulator
archives with the Apple SDK. Check the CI results for the revision being consumed;
configured jobs alone do not establish platform validation. iOS execution,
ARM desktop execution, and a complete iOS
Haxe/Lime application remain outside these checks.

HashLink field access uses generated native offsets. Staging its adapter checks
the host offsets against the checked-in extern provenance; a different layout
requires a matching generated extern set.

## Web ESM

Use `-D flight_esm`, `--macro EsmGenerator.use()`, and `-dce full` for static ESM
imports from the public TypeScript SDK. Import an ESM package facade from
`flight.esm` to access functions, constants, and host providers by their SDK
names. Public subpaths map to nested Haxe modules, such as
`flight.esm.scene2d_canvas.Contract`. The generated
`flight/esm/exports.json` lists package and type mappings.

```haxe
import flight.esm.HostWeb;
import flight.esm.Scene2DCanvas;

final surface = Scene2DCanvas.createCanvasElement(HostWeb.webHostCanvas, 640, 480);
final canvas = HostWeb.getWebSurfaceCanvasHandle(surface);
if (canvas != null) js.Browser.document.body.appendChild(canvas);
```

Use named Haxe type declarations from the listed `flight.esm.types` modules for
SDK types and typed class constructors. Type projection covers primitives,
collections, callbacks, promises, records, and nullable values. Complex
TypeScript unions and other shapes without a direct Haxe equivalent may use
`Dynamic`. The ordinary `flight.*` API also supports the ESM target for existing
cross-target consumers.

`tools/esm/buildWeb.mjs` compiles a Haxe consumer and bundles it against the pinned
Flight TypeScript sources with esbuild, without installing Flight's workspace
tooling. Apps can use their own bundler with matching published packages instead.
`npm run gate:web` resolves every generated SDK import from the consumer ZIP.
The gate compares each public entry point against the SDK exports linked by
esbuild. It exercises lifecycle, inherited fields and tree-shaking, and runs a
Haxe-generated host and Canvas render pass against the real SDK with a drawing
context double. The same render smoke can assert a pixel with a browser Canvas.
See the [ESM pipeline](tools/esm/README.md).

### Browser host handles

`flight.HostWeb` exposes Flight's existing browser Canvas and input-target
capabilities on the ESM target. Wrap an existing DOM canvas to acquire its 2D
surface, and release the Flight surface when finished. The DOM element remains
owned by the caller.

```haxe
import flight.HostWeb;

final capability = HostWeb.canvas;
final surface = HostWeb.createCanvasSurfaceFromNativeHandle(capability, canvas);
if (surface != null) {
    // Use the acquired surface.
    HostWeb.destroyCanvasSurface(capability, surface);
}

final input = HostWeb.createInputTargetHandle(canvas);
HostWeb.inputTarget.prepare(input);
```

The Canvas surface and input target are separate opaque Flight values. The browser
provider manages the association with the original DOM element. Use
`HostWeb.gl` with `createGlSurfaceFromNativeHandle` for WebGL2 or `HostWeb.wgpu`
with `createWgpuSurfaceFromNativeHandle` for WebGPU. WebGPU acquisition returns
a promise. Both return null when the browser cannot supply a context. Release
them with `destroyGlSurface` and `destroyWgpuSurface` respectively.

### App host seams

`flight.HostApp` exposes opaque app-window and app-loop handles on the ESM
target. Pass a host's attach and lifecycle capabilities into
`HostApp.attachWindow` to use an existing window. Use
`WindowAttachmentOwnership.Host` when the caller retains ownership of it.

- `flight.HostWeb` provides browser window attachment, lifecycle, and frame
  scheduling. Use `HostApp.startAppLoop` with `HostWeb.frameScheduler` and
  `HostWeb.lifecycle`, and stop or dispose the loop when finished.
- `flight.HostElectron.window(api)` and `flight.HostTauri.window(api)` supply
  Flight's window-attachment and lifecycle capabilities. Supply the respective
  shell SDK API object.
- `flight.HostCapacitor.appName(api)` supplies Flight's app-name capability
  from the injected Capacitor App plugin. Read it with `HostApp.getAppName`
  after Flight receives the plugin's app info.

## Develop and package

```sh
npm ci
npm run setup:native-tests          # Haxe 4.3.7, hxcpp, Neko, Lime 8.3.2
npm run rehydrate                  # pinned Rust Flight workspace
npm run generate -- --allow-network # initial Cargo dependency downloads
npm run native:build               # release binary + HL adapter for this host
npm run check                      # offline generation, package and runtime checks
npm run package:haxelib            # dist/flight-0.6.0.zip
```

Use Rust 1.96.0 as pinned in `rust-toolchain.toml`. The tools recognize a local
installation in `.artifacts/rust/{cargo,rustup}` and do not install Rust.
`setup:native-tests` may download project tools, including a local Neko on Linux;
it does not install system packages. A C/C++ compiler is also required.

Native builds are offline unless `--allow-network` is supplied. Select another
platform with `--platform <folder>` after installing its Rust target and native
SDK/toolchain. Build desktop HL adapters on their target host. `--hl-include`
or `HL_INCLUDE` selects a HashLink SDK; the default is Lime's bundled header.
`--without-hl` explicitly makes a cpp-only payload. `--profile dev` is available
for local checks; CI packages this development profile and labels its artifact
accordingly. To create a bindings-only ZIP, use
`npm run package:haxelib -- --externs-only`; native execution then needs binaries.

```sh
npm run generate:check              # generated Haxe and header drift
npm run check:externs:upstream      # Flight's own HL/cpp/JS check script
npm run gate:surface               # complete declaration surface + provenance
npm run test:native-producer       # Rust binding regression tests
npm run test:native-packaging      # patch identity and artifact rejection cases
npm run gate:package               # deterministic ZIP, declarations and ESM output
npm run gate:native-runtime        # installed ZIP: hxcpp/HL and real Lime consumers
npm run gate:web                   # installed ZIP: real ESM behavior + tree-shaking
```

`npm run check` stages a development binary before the native gates. Run
`native:build` again before producing a release-profile ZIP. Each platform's
manifest records its profile. See [extern intake](tools/externs/README.md) for
the source and generation contract.
