# flight-hx

Haxe externs generated by the Rust tooling in
[Flight](https://github.com/flighthq/flight), targeting native FFI and web ESM.
The transpiled Haxe implementation, separate TypeScript compiler dependency,
and flight-cpp adapters have been removed.

The source is Flight `develop` revision
`49c510e875461a9235b24ee846015ec1b47acd2a` plus the reviewable
[native producer patch](patches/flight/README.md). There are 3,409 generated Haxe
files selected from 5,724 C ABI exports. Generated Haxe is copied unchanged from
that producer; provenance records both the Flight revision and patch hashes.

## Consume

The haxelib name is `flight`. Install a release ZIP containing binaries for your
platform, then add `-lib flight` or use this in a Lime project:

```xml
<haxelib name="flight" />
```

`include.xml` selects native binaries, configures linking, and deploys shared
libraries. The package macro also supports ordinary hxcpp and HashLink builds
without Lime. Consumers do not need Rust, Cargo, or Node.

```haxe
import flight.Math;
import flight.Geometry;

final value = lerp(0, 10, 0.25);
final vector = createVector2(3, 4);
final length = getVector2Length(vector);
freeVector2(vector);
```

Native handles require the matching release function; allocation does not imply
automatic disposal. Unsupported targets and the removed `flight_hx` backend fail
at compile time.

## Native layout

```text
native/include/flight_ffi.h          generated C ABI declarations
native/bin/<platform>/              shared Flight runtime (.so/.dylib/.dll)
native/lib/<platform>/              iOS static archive or Windows import library
native/artifacts/<platform>.json    source identity and artifact checksums
ndll/<platform>/flight.hdll         HashLink adapter
```

Ordinary shared libraries live in `native/bin`; `ndll` is used only for the
HashLink adapter selected by Lime's native module machinery. The binaries and
artifact manifests are ignored by Git. Release ZIPs include the staged platforms
after checking their provenance and checksums. An unstaged platform fails with
a missing-binary error instead of falling back to another implementation.

Platform folders are `Linux64`, `LinuxArm64`, `Mac64`, `MacArm64`, `Windows64`,
`iPhoneOSArm64`, `iPhoneSimulator64`, and `iPhoneSimulatorArm64`. Desktop hxcpp
links the shared library; iOS links `libflight_ffi.a`. For a cross build, set
`flight_native_platform` before the Flight haxelib entry, for example:

```xml
<set name="flight_native_platform" value="iPhoneSimulatorArm64" />
<haxelib name="flight" />
```

The Linux x64 checks run a consumer installed from the ZIP through hxcpp,
HashLink, Lime Linux, and Lime HashLink. HashLink also loads the entire generated
native declaration surface. The smoke calls cover scalar math, allocation,
field access/mutation, and release. This does not establish every API's runtime
behavior. macOS, Windows, ARM, and iOS have build/link configuration but have not
been built or run by these Linux checks. In particular, iOS needs validation
with the Apple SDK and any required final application system libraries.

HashLink field access uses generated native offsets. Staging its adapter checks
the host offsets against the checked-in extern provenance; a different layout
requires a matching generated extern set.

## Web ESM

Use `-D flight_esm`, `--macro EsmGenerator.use()`, and `-dce full` for static ESM
imports. The externs expect a module named `flight` exporting `flight_*`
functions, including field accessors. They do not directly consume the older
`@flighthq/*` TypeScript modules. A matching ESM runtime remains a separate
integration task; the checks verify declarations and import emission only.

## Develop and package

```sh
npm ci
npm run setup:native-tests          # Haxe 4.3.7, hxcpp, Neko, Lime 8.3.2
npm run rehydrate                  # pinned Rust Flight workspace
npm run generate -- --allow-network # initial Cargo dependency downloads
npm run native:build               # release binary + HL adapter for this host
npm run check                      # offline generation, package and runtime checks
npm run package:haxelib            # dist/flight-0.6.0.zip
```

Use Rust 1.96.0 as pinned in `rust-toolchain.toml`. The tools recognize a local
installation in `.artifacts/rust/{cargo,rustup}` and do not install Rust.
`setup:native-tests` may download project tools, including a local Neko on Linux;
it does not install system packages. A C/C++ compiler is also required.

Native builds are offline unless `--allow-network` is supplied. Select another
platform with `--platform <folder>` after installing its Rust target and native
SDK/toolchain. Build desktop HL adapters on their target host. `--hl-include`
or `HL_INCLUDE` selects a HashLink SDK; the default is Lime's bundled header.
`--without-hl` explicitly makes a cpp-only payload. `--profile dev` is available
for local checks; CI packages this development profile and labels its artifact
accordingly. To create a bindings-only ZIP, use
`npm run package:haxelib -- --externs-only`; native execution then needs binaries.

```sh
npm run generate:check              # generated Haxe and header drift
npm run check:externs:upstream      # Flight's own HL/cpp/JS check script
npm run gate:surface               # complete declaration surface + provenance
npm run test:native-producer       # Rust binding regression tests
npm run test:native-packaging      # patch identity and artifact rejection cases
npm run gate:package               # deterministic ZIP, declarations and ESM output
npm run gate:native-runtime        # installed ZIP: hxcpp/HL and real Lime consumers
```

`npm run check` stages a development binary before the native gates. Run
`native:build` again before producing a release-profile ZIP. Each platform's
manifest records its profile. See [extern intake](tools/externs/README.md) for
the source and generation contract.
